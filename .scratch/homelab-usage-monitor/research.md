# Provider usage visibility: research evidence

Researched 2026-10-08. This is factual evidence for a design interview, not an implementation specification or an integration decision. Only public official documentation and first-party source were inspected. No local credentials, account data, login flows, collectors, builds, tests, hardware operations, or issue operations were used.

## Terms and existing decision

The repository distinguishes a **usage window**, **window reset time**, **banked reset**, **manual reset**, and **banked reset expiry**. An unavailable reading is not zero usage ([CONTEXT.md](../../CONTEXT.md), lines 7–29). ADR-0001 selects experimental private Codex usage/reset-credit endpoints on the ESP32 and explicitly keeps manual reset on the website ([ADR](../../docs/adr/0001-codex-usage-source.md), line 3). Moving provider collection to a Rust homelab server changes that existing source-location decision. Adding Claude also expands the Codex-only context. No ADR or firmware was changed here.

## What the numbers mean

- Subscription percentages measure consumption of a provider-defined allowance during a usage window. They are not percentages of a context window, raw token totals, or a dollar bill. Claude Code exposes distinct `context_window`, `cost`, and `rate_limits` objects; Codex exposes window `usedPercent`, duration, and reset timestamps separately from account token activity ([Claude statusline](https://code.claude.com/docs/en/statusline#available-data), [Codex app-server](https://developers.openai.com/codex/app-server#auth-endpoints)).
- Codex explicitly says API token prices are separate from subscription usage and must not estimate included tasks. Allowance consumption depends on model, context, reasoning, tools, retrieval, caching, and speed. Local and cloud work share plan allowance; weekly limits may apply. Current pricing documentation says Plus and Standard Business have five-hour limits, while Pro does not. Do not hardcode a five-hour window for every account ([pricing](https://developers.openai.com/codex/pricing)).
- Claude `/usage` session dollars are calculated locally at list price or configured rates and are estimates. Included Pro/Max usage is not billed according to that session dollar number. Plan usage bars and recent local attribution are separate: the attribution breakdown excludes other devices and claude.ai ([costs](https://code.claude.com/docs/en/costs#using-the-usage-command)).
- [INFERENCE] Percentages from Claude and Codex cannot produce one meaningful pooled percentage without inventing a common denominator. A simultaneous overview can preserve provider-specific values without claiming interchangeable allowances.

## Claude / Claude Code

### Documented subscription visibility

- Claude Code `/usage` shows plan usage bars, session usage, activity statistics, and usage attribution. `/status` reports account/model/configuration/connectivity information rather than serving as the quota-percentage view ([commands](https://code.claude.com/docs/en/commands), [costs](https://code.claude.com/docs/en/costs)).
- The documented statusline command receives JSON on stdin. Subscription fields are `rate_limits.five_hour.used_percentage`, `rate_limits.seven_day.used_percentage`, and each window's `resets_at`. Percentages are consumed allowance, 0–100; reset times are Unix epoch **seconds**. The five-hour window is rolling; `seven_day` is weekly ([statusline, rate-limit usage](https://code.claude.com/docs/en/statusline#rate-limit-usage)).
- Important availability limit: statusline documentation says this subscription `rate_limits` object appears only for **Pro and Max**, and only after the session's first API response. Gateway spend limits are another supported use of the object, not personal subscription quota. Each window may be absent; Claude Code drops a window after its reset time passes. `/usage` supporting Team/Enterprise does not establish that the statusline exposes their same bars ([statusline, available data](https://code.claude.com/docs/en/statusline#available-data)).
- Statusline scripts run at session start, new assistant messages, other session events, an optional refresh timer, and a previously received window's reset time. Running the script itself consumes no API tokens. This is a documented local session interface, not a documented standalone server polling API. [INFERENCE] A timer rerunning a script must not be assumed to fetch fresh account data independently of Claude Code's own session state ([statusline](https://code.claude.com/docs/en/statusline#how-status-lines-work)).
- `/usage` can show a locally cached quota snapshot fetched within the previous **60 minutes** when the usage request fails, with a last-known-data notice. Freshness and quota unavailability therefore need to remain distinct from zero usage ([costs, failed usage request](https://code.claude.com/docs/en/costs#when-the-usage-request-fails)).
- No banked-reset credit count, per-credit expiry, or manual-reset API is documented in the examined Claude statusline/usage sources. Claude **usage credits** are paid continuation beyond an allowance, not Codex banked reset credits ([costs, usage credits](https://code.claude.com/docs/en/costs#add-usage-credits-to-your-subscription)).

### Documented API usage is different

- Anthropic provides public APIs for historical organization **API** usage and cost: `/v1/organizations/usage_report/messages` and `/v1/organizations/cost_report`. Usage provides token categories with minute/hour/day buckets; cost provides daily USD amounts represented as decimal strings in cents. These do not document personal Claude subscription quota windows ([Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)).
- A public Rate Limits API also exists: `/v1/organizations/rate_limits` reads configured organization/workspace limits for Messages API and supporting resources. Values include requests/input tokens/output tokens per minute; this is not a personal plan consumed-percentage endpoint ([Rate Limits API](https://platform.claude.com/docs/en/manage-claude/rate-limits-api)).
- These Admin APIs are explicitly unavailable for individual accounts. Current documentation permits an Admin key, `org:admin` OAuth token, or eligible personal/service key not scoped to a workspace; workspace keys do not work. Enterprise claude.ai analytics uses a different Analytics key/API, not the Console Admin key ([Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api), [Rate Limits API](https://platform.claude.com/docs/en/manage-claude/rate-limits-api)).
- Bounded finding: after checking current subscription usage, statusline, authentication, legal, usage/cost, and rate-limit documentation, **no public documented personal subscription quota polling endpoint was found**. This is not a claim that no internal endpoint exists. Public issue reports mentioning `/api/oauth/usage` are user-generated content, not a supported API contract; no external collector authorization or stability guarantee was established from them.

### Authentication and storage boundary

- The supported user flow is signing into the unmodified Claude Code binary with a Claude account, or using API/provider credentials for API billing. Claude Code manages macOS subscription credentials in encrypted Keychain, with a `0600` credentials-file fallback; Linux uses `~/.claude/.credentials.json` with `0600`; Windows uses the profile credentials file and inherited account access controls. `CLAUDE_CONFIG_DIR` separates configuration and corresponding credential storage ([authentication](https://code.claude.com/docs/en/authentication#credential-management)). These are documented paths only; no contents were read.
- `claude setup-token` creates a one-year token for Claude Code scripts/CI, supplied through `CLAUDE_CODE_OAUTH_TOKEN`. Documentation says it can **only make model requests**. Its existence does not establish permission or sufficient scope for quota HTTP polling ([authentication, long-lived token](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token)).
- Anthropic restricts subscription OAuth to ordinary use of Claude Code/native apps. Third-party developers may not offer Claude.ai login, collect/store/intermediate Claude.ai credentials/session tokens, or route requests through personal-plan credentials on users' behalf. Users may sign into unmodified Claude Code with their own subscription, including on a hosting platform satisfying stated conditions. Direct Rust reuse of subscription tokens is therefore not established as an authorized integration; a personal collector exception was not found ([legal and compliance](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use)).

## ChatGPT / Codex

### Documented quota and reset information

- `/status` in an active Codex CLI session shows remaining limits; the website has a usage dashboard. `codex login status` reports authentication and is not the same quota interface ([pricing](https://developers.openai.com/codex/pricing#where-can-i-see-my-current-usage-limits), [authentication](https://developers.openai.com/codex/auth)).
- There is now a documented first-party machine interface: Codex app-server JSON-RPC `account/rateLimits/read` and `account/rateLimits/updated`. Windows expose `usedPercent`, `windowDurationMins`, and `resetsAt` in Unix **seconds**. `rateLimitsByLimitId` permits multiple buckets; `planType`, credit information, labels, and reached-limit classification can be provided. Window and timestamp fields can be null ([app-server](https://developers.openai.com/codex/app-server#auth-endpoints), [window schema](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/RateLimitWindow.ts), [snapshot schema](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/RateLimitSnapshot.ts)).
- The same documented read can include `rateLimitResetCredits.availableCount` and per-credit `id`, `status`, `grantedAt`, `expiresAt`, `title`, and `description`. The summary may be null; `credits: null` means details unknown, while an empty array means details were fetched and none returned. Detail rows may be capped, so the count remains authoritative ([app-server](https://developers.openai.com/codex/app-server#auth-endpoints)).
- The first-party response schema additionally contains nullable `ordinaryUsageAllowed`. Its comment explicitly prohibits inferring recovery from percentages/reset times when permission is unavailable ([response schema](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/GetAccountRateLimitsResponse.ts)).
- App-server also documents **mutating** `account/rateLimitResetCredit/consume`. Its availability is not authorization to add a reset button: the repository's read-only ADR still excludes applying manual resets. `account/usage/read` separately reports lifetime/peak/daily token activity, not Platform API dollar costs; metrics can be null and API-key-only authentication does not support that account usage read ([app-server](https://developers.openai.com/codex/app-server#auth-endpoints)).
- This is a local Codex protocol, not evidence of a general-purpose public REST endpoint for every ChatGPT product/model quota. Codex documentation now says ChatGPT Work shares usage with Codex, and other agentic features can share allowance; ordinary ChatGPT conversation limits should not be inferred as completely represented by the Codex response ([pricing](https://developers.openai.com/codex/pricing)).

### Authentication, deployment, and stability

- Codex supports managed ChatGPT browser/device-code authentication for subscription access and API keys for separately billed API access. Managed login stores and automatically refreshes tokens. Device-code login is documented for headless environments, subject to enabled account/workspace settings. Official docs also describe protected auth-cache transfer to a headless host/Docker as a fallback ([authentication](https://developers.openai.com/codex/auth#login-on-headless-devices)). No login or transfer was executed.
- Credential storage options are `file`, `keyring`, `auto`, and `ephemeral`. `file` uses `auth.json` under `CODEX_HOME`; `auto` may fall back from an OS credential store to plaintext file. The docs explicitly require treating the auth file like a password. Automatic refresh implies persistence of updated credentials rather than assuming a copied snapshot lasts indefinitely ([authentication](https://developers.openai.com/codex/auth#credential-storage)).
- App-server requires `initialize` then `initialized`. It offers stdio and other transports. WebSockets are explicitly experimental/unsupported; non-loopback listeners can permit unauthenticated connections by default. The developer-command reference says app-server is primarily for development/debugging and can change without notice. Documented protocol does not mean zero stability risk, and live `main` source does not prove the user's installed release has every field ([app-server](https://developers.openai.com/codex/app-server), [developer commands](https://developers.openai.com/codex/developer-commands)).
- Important permission boundary: current app-server auth docs state existing local/open-source integrations may continue but **app-server authentication has never been permitted for commercial or hosted services**, recommending Sign in with ChatGPT (SIWC) ([auth endpoints](https://developers.openai.com/codex/app-server#auth-endpoints)). Do not silently classify the proposed private Docker homelab as permitted or prohibited by that sentence.
- New SIWC documentation explicitly covers open-source/locally hosted clients and self-hosted VMs. It uses the app's own OAuth registration and stable host ID, with protected credentials and host-owned token refresh. It documents plan-backed `/v1/responses` inference; this evidence does **not** establish that SIWC tokens can read existing Codex service quota/reset-credit RPCs. Its app-server example configures a custom Responses provider with `requires_openai_auth=false`, not managed Codex ChatGPT login ([SIWC overview](https://developers.openai.com/siwc/token-sharing-open-source), [self-hosted VMs](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms), [app-server configuration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server), [preview limits](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)).
- SIWC tokens have documented one-hour access-token and 30-day refresh-token lifetimes; refresh returns a replacement refresh token. Refreshes for one session must be serialized. Tokens belong in protected runtime storage, never browser storage, URLs, logs, source control, or support transcripts. These lifetimes apply to SIWC, not automatically to existing Codex auth-cache tokens ([token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference), [accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)).

### Direct backend HTTP and API costs

- First-party Rust source verifies the internal paths `/wham/usage` and `/wham/rate-limit-reset-credits` (and equivalent `/api/codex/...` forms). The reset `consume` path is a POST, unlike usage reads. Source revision inspected: `e974aad3b1a8f144273e882c614aefe69eaef615` ([pinned source](https://github.com/openai/codex/blob/e974aad3b1a8f144273e882c614aefe69eaef615/codex-rs/backend-client/src/client/rate_limit_resets.rs)). These are backend implementation routes, not the documented public Platform API usage contract. [INFERENCE] Copying them into a Rust collector couples it directly to backend schemas/authentication changes; official source visibility does not grant support or credential permission.
- OpenAI Platform provides documented organization API metering through `/organization/usage/completions` and `/organization/costs`, distinct from Codex subscription windows. Organization Admin APIs use an Admin key, not the user's ChatGPT login. Usage includes input/output/cache tokens, model/project/key filters, and time buckets; cost reporting uses daily buckets ([Usage reference](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage), [Costs reference](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/costs), [Admin APIs](https://developers.openai.com/api/docs/guides/admin-apis)).

## Unanswered decisions and bounded gaps

1. Which accounts/plans are involved: Claude Pro/Max versus Team/Enterprise/API, and Codex Plus/Pro/Business/API? Plans change which windows and interfaces exist.
2. Does “usage” mean subscription allowance only, or also paid continuation credits, API tokens/cost, and activity statistics? Keep these quantities separate.
3. Does “reset” mean window reset countdown only, Codex banked reset count/per-credit expiry, or applying a manual reset? Applying one contradicts the current read-only ADR.
4. Must monitoring stay fresh with every coding machine/CLI closed? Claude statusline is session-bound; a continuously polled authorized personal quota API was not established.
5. Is a machine-side relay of documented quota-only CLI data acceptable, or must the Docker server own provider authentication? No final choice is made. Provider permission and refresh ownership must be settled before any credential provisioning.
6. Which authentication route is authorized for this personal homelab? Codex's older app-server authentication restriction and newer SIWC self-hosted flow are distinct. SIWC quota/reset-read coverage remains unestablished. Claude's external subscription-token boundary remains a constraint.
7. Which additional model-specific windows, credit balances, or account metadata must fit the provider dashboards? The documented Claude statusline contains only the named subscription windows, while Codex can return multiple buckets.
8. What maximum data age is acceptable, and how should unavailable/stale readings appear? The domain already rejects representing unavailable usage as 0%.

No endpoint was called with authentication. No actual account quota response, installed CLI capability, supported polling frequency, or provider permission for a bespoke token-based collector was verified. The findings establish available public interfaces and constraints, not a selected integration.
